# apps/api

The NestJS API (ADR 0002, ADR 0020): REST under `/api`, Express, ESM, on Node 24. Every route goes through the core: access guard, error filter, response serialization through its contract schema.

## Layout
- `src/main.ts` starts the process; `src/app.module.ts` (`AppModule.forRoot(config)`) imports the core and every module; `src/app.ts` (`configureApp`) holds what production and tests both apply (prefix, shutdown hooks, CORS). CORS answers only the clinic app's fixed origins (`clinicOrigins`: `app://clinic`, plus Vite's `http://localhost:5173` outside production), never a reflected origin, without credentials, with the headers `authorization`, `content-type`, `x-device-token` and `x-sign-in-ticket`; console routes answer no CORS (same-origin, cookie and `Origin` check). Pinned by `test/cors.test.ts`.
- `src/core/config/`: the environment checked by Zod at start-up (`loadConfig`), provided as `CONFIG`.
- `src/core/database/`: `DATABASE`, the one Drizzle database of the process, connected as the app role; the pool closes on shutdown.
- `src/core/access/`: `@Public()`, `@PatientRoute()`, `@StaffRoute(...permissions)` (any of them; none: any signed-in member), `@ConsoleRoute(permission?, { reauth? })` (a platform role holding it; `reauth`: a TOTP in the last 5 minutes), `@ConsoleSignInRoute()` (the public console sign-in steps), `@DeviceRoute({ allowRevoked?, ticket? })`, `@TicketRoute(purpose)`, `@RequiresFeature(key)`, `@NoFeature()`, and `AccessGuard`, global and fail-closed. It checks tokens through the `SESSION_VERIFIER` port (`session-verifier.ts`, provided by the identity module): staff access token in `Authorization: Bearer`, device token in `x-device-token`, sign-in ticket in `x-sign-in-ticket`, console session in the `__Secure-vertex-console` cookie (`HttpOnly`, `Secure`, `SameSite=Strict`, path `/api/console/`); console writes, sign-in steps included, must carry `Origin: CONSOLE_ORIGIN`. `actor.ts`: the `Actor` types (staff with tenant, membership, account, session, device, branch scope and effective permissions; platform; system), `DeviceActor`, `Ticket`, `holds(actor, permission, facilityId?)` for branch-scoped checks in services, and `@CurrentStaff()`, `@CurrentPlatformUser()`, `@CurrentDevice()`, `@CurrentTicket()`.
- `src/core/rate-limit/`: `RateLimiter`, a fixed window per key in the process's memory.
- `src/core/concurrency/`: `assertCurrent` (an edit's `expectedUpdatedAt`, else `CONFLICT`) and `nextUpdatedAt`, for every optimistic online edit.
- `src/core/uploads/`: `RejectedUpload`, the interceptor that turns multer's refusals into `FILE_REJECTED` (logo and doctor photo uploads).
- `src/core/serialization/`: `ContractSerializer`, the response serializer; it checks an array response as a whole against its list schema.
- `src/core/errors/`: `ErrorFilter` (every error leaves as `{ code, message }` with the status of its code). `describeForLog` (what an unexpected error may write to the log) comes from `@vertex-shifa/db`, shared with the worker.
- `src/core/health/`: `GET /api/health` (in the core because `health` is a layer name).
- `src/core/routes.ts` (`listRoutes`) and `src/core/openapi/` (`buildOpenApiDocument`): the routes with their declarations, and the OpenAPI 3.1 document built from them and the contracts.
- `src/modules/<platform|health|clinic>/<module>/`: one folder per module (ADR 0020 anatomy). The pattern to copy is `modules/platform/tenancy/`: controllers for staff and console routes, a service whose writes run in `withTenant` with the tenant row locked and the audit entry in the same transaction, `index.ts` as the public surface. `modules/platform/audit/` holds `recordAudit(tx, tenantId, entry)` and `recordPlatformAudit(tx, entry)`; `modules/platform/events/` holds `publishEvent(tx, tenantId, type, payload)` (the outbox, types from the event catalog in `packages/contracts`). `modules/platform/identity/` (sign-in, OTPs, tickets, devices and their management, sessions, the JWKS; the console's platform users, sign-in with TOTP and recovery codes, cookie sessions, owner recovery routes) is global: it provides the ports other modules declare (`SESSION_VERIFIER` in the core, `FACILITY_DEVICES` in tenancy, `STAFF_ACCOUNTS` and `MEMBER_DEVICES` in access); `modules/platform/access/` reads memberships for it and holds staff management, which reaches accounts, computers and doctor profiles only through the ports in `access/ports.ts`. `modules/health/practitioners/` (doctor profiles, specialties, photos) is global for the same reason: it provides access's `PRACTITIONER_PROFILES`, which staff management and `/api/me` use. A port is how a lower layer, or a module that another already imports, uses data it does not own.
- `src/cli/`: the API CLI (`main.ts`, one file of commands per area: `tenant-commands.ts`, `account-commands.ts`, `platform-user-commands.ts`), run as the app role on the API's `.env`; it calls module services as the `system` actor.
- `test/`: integration tests over HTTP against a fresh migrated database per run (`test/global-setup.ts`, `createTestApp` in `test/app.ts` with identity keys made per run; `StaffClient` in `test/staff.ts` signs staff in over HTTP as the clinic app does, `ConsoleClient` in `test/console.ts` platform users as the console does); `test/architecture/` the architecture test; `test/openapi.test.ts` the drift test. Unit tests sit next to the code (`*.test.ts`).
- `openapi.json`: the committed OpenAPI document, generated (responses, request bodies, path and query parameters, the multipart logo and doctor photo uploads); never edit it by hand.

## Rules
- Inputs are parsed by the global validation pipe from the schema on the parameter: `@Body({ schema })`, `@Query({ schema })`, `@Param('id', { schema: z.uuid() })`. A refusal is `VALIDATION_FAILED` naming the fields, never their values.
- Every route declares one access decorator and one entitlement decorator (`@RequiresFeature(key)` or `@NoFeature()`), on the handler or its controller, and its response schema with `@SerializeOptions({ schema })`, a contract schema with `.meta({ id })`. The serializer answers only the schema's fields, so handlers never take `@Res()` or `@Next()`. Console routes (`@ConsoleRoute`, `@ConsoleSignInRoute`), and only they, live under `/api/console/`, in `<module>.console.controller.ts`; one that opens or ends a session returns `WithConsoleCookie` and takes `@UseInterceptors(ConsoleSessionCookie)`, which writes the `Set-Cookie` header. The architecture test enforces the declarations, the schema, the console path (including `RouterModule` paths and inherited handlers) and the absence of `@Res()`/`@Next()`.
- Staff, device and ticket routes are checked against verified tokens and the database on every request (session open, device active, enrollment, membership active, branch scope, tenant status). Console routes are checked the same way (session open, 12 hours absolute, 30 minutes idle, user active, role, re-authentication) and each one writes a `console.request` row to the platform audit before its role and re-authentication are checked. Patient routes (S19) still refuse with `UNAUTHENTICATED`, and every route needing a feature with `NOT_ENTITLED` until S05. A spec replaces a refusal with a real check; it never loosens the fail-closed default.
- A branch-scoped permission (`facility.manage`, `devices.manage`) admits the member at the guard if held in any branch: the service checks the resource's branch with `holds(actor, permission, facilityId)`.
- Secrets (OTP codes, refresh tokens, console session tokens, setup and recovery codes, rate-limit keys of phones and addresses) are stored as keyed hashes (`KeyedHash`); secrets the server reads back (TOTP secrets) sealed with `SecretBox` (AES-256-GCM, `IDENTITY_ENCRYPTION_KEY`, bound to their row); passwords with Argon2id; phones and names never reach logs or rate-limit keys in clear. Answers to unknown phones match those to known ones (decoys in `OtpChallenges`, the decoy password check and `DecoyLocks` in `AuthService` and `ConsoleAuthService`).
- Injection is always explicit: `constructor(@Inject(TOKEN) private readonly x: X)`. No decorator metadata is emitted (`@vertex-shifa/config/tsconfig/nest.json`), so an implicit parameter would be `undefined`; the architecture test catches it in providers, controllers, guards, interceptors, pipes, filters and middleware.
- Tenant data only inside `withTenant(db, tenantId, tx => …)` from `@vertex-shifa/db`, with the tenant from the session or device, never from the request body or query (ADR 0004). Two exceptions, both rechecked under that tenant's isolation: `POST /api/devices` takes the clinic chosen from the registration options and checks the signed-in account's membership there; `POST /api/devices/token` reads the device under the tenant the installation names and trusts the pair only once the device key's signature verifies.
- A business refusal throws `DomainError(code, message)` from `@vertex-shifa/contracts`; the message is English, for logs, and carries ids at most, never medical data. Never log request bodies, query parameters or a database error's message: use `describeForLog`.
- Modules reach each other only through `index.ts`, and only in their own layer or below (clinic → health → platform); the core imports no module. The architecture test enforces this.
- A change to a route or a contract schema changes `openapi.json`: regenerate it with `pnpm --filter @vertex-shifa/api exec vitest run -u test/openapi.test.ts` and review the diff.

Run: `pnpm --filter @vertex-shifa/api test` (needs the local database, `packages/db/CLAUDE.md`).
